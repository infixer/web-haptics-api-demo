## 1. 導入: まずデモ（0:00–1:30）

**見せる画面:** `/lab`。最初はコードや経緯を説明しない。

**操作の順番**

1. Androidタブで「タップ」→「完了」→「エラー」を押す。
2. 振動の長さを変え、同じパターンをもう一度押す。
3. ノッチのスライダーをなぞる。
4. iOSタブでスイッチ本体と「お気に入り」を直接タップする。

**話すこと**

- 「今日はまず、触ってみてください。画面の操作に感触を足すデモです」
- 「今の感触が、Webからどう生まれているのかを順に見ていきます」

**発表者メモ:** 会場の映像だけでは振動は伝わらない。実機を手元で体験してもらうか、触った本人の感想を添える。URLを案内する場合は、実際に公開・動作確認したHTTPSの `/lab` を使う。ローカルホストは参加者のスマホから開けない。

**つなぎ:** 「この、操作に返ってくる感触をHapticsと呼びます」

## 2. Hapticsとは何か（1:30–2:30）

**一番伝えたいこと:** 触覚を通じて、操作や状態を伝えるフィードバック。

- 例: スイッチが切り替わる、ピッカーが一段進む、ドラッグしたものが所定の位置にはまる。
- 押せた・選べた・端に着いたことを、視覚や音に加えて指先で伝える。
- Hapticsは振動だけに限らない。今回はスマホの振動による触覚に範囲を絞る。
- いつ返すか、どれくらい続くか、どんなリズムかで、同じ操作の印象も変わる。

**つなぎ:** 「ではWebでも、その意味に合わせて感触を指定できるのでしょうか」

## 3. Web Haptics APIの紹介（2:30–4:00）

**一番伝えたいこと:** 波形の数値を組み立てる代わりに、操作の意味を指定する提案。

| | Vibration API | Web Haptics APIの提案 |
|---|---|---|
| 指定するもの | 振動時間・休止時間 | `hint` / `tick` / `align` / `edge` とintensity |
| JavaScript | `navigator.vibrate([35, 70, 55])` | `navigator.playHaptics("tick", 0.7)` |
| CSS | このAPI自体には宣言的な指定なし | `@haptic` も提案 |
| このLTでの位置づけ | Androidデモで使用するAPI | 将来の仕組みとして紹介する提案 |

**見せるコード（提案の構文例）**

```js
// 一段進んだことを伝える
navigator.playHaptics("tick", 0.7);
```

```css
/* 提案中の構文。そのまま現行ブラウザで動く前提ではない */
button:active {
  @haptic tick 0.7;
}
```

**話すこと**

- `hint`: 操作を促す軽い合図。`tick`: 一段進む。`align`: 位置が合う。`edge`: 境界に達する。
- 要求を端末側の表現に対応づける。同じ触感を全端末に保証するものではない。
- まだ初期段階の提案。今日の `/lab` がこのAPIのブラウザ実装で動いているわけではない。

出典: [WICG/web-haptics](https://github.com/WICG/web-haptics)（2026-09-11確認）。

**つなぎ:** 「この提案を先に体験したくて、polyfillを作ってみました」

## 4. 最初に試したこと（4:00–5:00）

**見せるもの:** 呼び出しから出力先への簡単な対応。

```text
navigator.playHaptics()
  ├─ Android: navigator.vibrate()
  └─ 当初のiOS案: 隠したswitchをlabel.click()
```

- ノッチ付きスライダーと触覚あてゲームを作った。
- 当初はiOSのswitchハックで、スクリプトから触覚を出せると考えていた。
- 操作すると画面のモニタは動く。しかしiPhoneでは何も感じなかった。

**ここでの問い:** 「画面が反応したことと、モーターが動いたことは同じなのか？」

根拠: [既存検証ログ](FINDINGS-ios-switch.md)。Gamepadや音のシミュレータの話は、10分では本筋から外れるため省略する。

## 5. ログ: 同じ要素で条件を変えた（5:00–6:30）

**見せるもの:** 2026-09-09の記録を要約した比較表。

| 操作 | 記録されている実機結果 |
|---|---|
| 可視switchを指で直接タップ | 鳴った |
| 隠したswitchを `label.click()` | 鳴らなかった |
| 可視switchを `label.click()` | 鳴らなかった |
| その同じ可視switchを指でタップ | 鳴った |

- 位置や透明度だけが問題ではない。同じ要素でも操作経路で結果が分かれた。
- ボタンの操作直後に同期的に呼んでも、合成クリックでは鳴らなかった。
- 「Webでは一切鳴らせない」ではなく、「このスクリプト経路では鳴らなかった」と結論を絞る。

**発表者メモ:** 元ログの端末はiPhone SE / Safari。世代と正確なOSバージョンは未記録。これを最新版の全iPhoneで検証済みとは言わない。

**つなぎ:** 「直接の操作と合成クリックの違いは、実装にも現れていました」

## 6. 再調査: trusted判定を見落としていた（6:30–7:30）

**一番伝えたいこと:** 失敗の原因だけでなく、調査の結論も更新した。

- 最初の調査では「公開WebKitに、この現象を説明するコードが見つからない」と記録した。
- 再調査では、触覚処理に入る手前の `state.trusted` 判定が見つかった。
- 関連labelへの合成クリックがtrustedとして伝わる問題も、公開修正の対象になっていた。
- user activationがあることだけでは、そのクリックがtrustedになるわけではない。

**見せる範囲:** 判定の要点1行と、修正へのリンクだけ。大量のC++は出さない。

出典: [WebKit CheckboxInputType.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/html/CheckboxInputType.cpp)、[labelの合成クリックに関する修正](https://github.com/WebKit/WebKit/commit/4a8a90644cfc7a9a4b3cab13c4c0b49c53862787)。

**発表者メモ:** iOS 26.5からという第三者報告と、自分の実機記録は区別する。修正の公開日だけでOSへの搭載日を断定しない。訂正の詳細は[再調査文書](RESEARCH-mobile-haptics-2026-09.md)。

## 7. いまのデモへ作り直した（7:30–9:00）

**見せるもの:** 冒頭のデモを、今度は仕組みが分かった状態で振り返る。

| | 作り直した方法 | 残る制約 |
|---|---|---|
| Android | 配列でリズムを送り、パルスの長さを調整 | 振幅の制御ではない。端末ごとの感触に差がある |
| iOS | 実switchを指で操作。お気に入りにも透明なswitchを重ねる | 自動連打・任意の強さの指定はできない。タッチを奪ってスクロールに影響することがある |

- Androidは短いパルスだけで判断せず、200msの基準でも確認できるようにした。
- iOSは `.click()` を呼ばず、指が実際のinputに当たるようにした。
- モニタや戻り値だけで成功扱いにしない。手で感じた結果を別に確認する。
- デモ画面は操作だけに絞り、調査の経緯は資料側に置いた。

**発表者メモ:** このリポジトリでの最新版Androidの実振動と、新しい透明switchデモの実機結果は、現時点の記録では未検証。発表前に確認できた場合だけ、機種・OS・ブラウザ・感触を追記する。

## 8. まとめ（9:00–10:00）

**持ち帰ってほしい3点**

1. Hapticsは操作の結果を指先に返す表現。Webでも使える経路はある。
2. 現在のAndroidとiOSでは、できることも方法も違う。
3. Web Haptics APIは操作の意味を指定する提案。polyfillや画面の反応だけでは、その実現を保証できない。

**締めの一言:** 「APIを呼べたところがゴールではなく、指に届いたところまで確かめる必要がありました」

## 発表前の準備メモ（投影しない）

- 公開済みの `/lab` を実機の通常タブで開き、当日使う操作を確認する。
- 冒頭の操作は90秒で終わらせる。振動が出なければ何度も試さず、条件を記録して話を進める。
- 画面収録は操作の補助資料として使えるが、振動の証拠にはしない。
- 合成クリックとの対照が必要なら既存の `/probe` を発表者用に使う。通常の `/lab` には比較機能を戻さない。
- 記録欄: 実施日 / 機種 / OS / ブラウザ / 操作 / 感じた結果。未確認は未確認のまま残す。
