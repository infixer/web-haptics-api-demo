# 他のアプリ案

> **実装済み:** このうち **#1 触覚ノッチ付きスライダー** と **#6 触覚あてゲーム / 神経衰弱** を
> `apps/web` に作りました。#3 会場同期バイブは「フロントエンドのみ」の方針により見送り
> （Durable Objects が必要なため）。以下は今後の候補として残します。


Web Haptics API を題材にした勉強会デモとして、モールス以外に作れそうなもの。

**評価軸:**
- **API 適合** — Web Haptics API の 4 エフェクト（`hint`/`edge`/`tick`/`align`）で素直に書けるか
- **実装コスト** — 数時間 / 半日 / 1日以上
- **LT 映え** — 会場で体験させたときのインパクト

---

## 0. まず「型」を意識する

LT の構成として強いのは、**API の想定内と想定外を両方見せる**こと。

| 立ち位置 | 意味 | 該当案 |
|---|---|---|
| **A. 正の例** | API が「まさにこのために」作られた使い方 | #1 スライダーのノッチ, #4 ナビ |
| **B. 境界の例** | API の表現力の外側に落ちる使い方 | **モールス（本体）**, #2 呼吸ガイド |
| **C. 体験の例** | 理屈より先に「おおっ」となる使い方 | #3 会場同期, #6 触覚あてゲーム |

**モールス（B）だけだと「使えない API」の話に聞こえてしまう。**
A を 1 つ添えると「適材適所である」という公平な結論に着地できる。
→ **#1 は最優先で作ることを推奨。実装コストも最小。**

---

## 1. 触覚ノッチ付きスライダー / カラーピッカー ★最推奨

**「Web Haptics API はこれのために作られた」を 30 秒で示す最短の例。**

- スライダーを 5% 刻みで動かすと `tick`
- 端（0% / 100%）に当たると `edge`
- スナップポイント（50% など）に吸い付くと `align`
- 掴めるハンドルにポインタが乗ると `hint`

```css
/* CSS だけで書ける、というのがこの API の狙い */
input[type=range]::-webkit-slider-thumb:hover { @haptic hint 0.4; }
```

| API 適合 | 実装コスト | LT 映え |
|---|---|---|
| ★★★（4 エフェクト全部が自然に出てくる） | 数時間 | ★★☆ |

**推し所:** 4 つのエフェクト名が「なぜこの 4 つなのか」が触った瞬間に腹落ちする。
モールスの直前に置くと、**「じゃあ duration が要る用途は？」**という流れが作れて構成が綺麗。

## 2. 呼吸ガイド / 瞑想ペーサー

4-7-8 呼吸法（4 秒吸う・7 秒止める・8 秒吐く）を振動で誘導。**画面を見ずに使える**のが本質的価値。

- 吸う: だんだん強くなる 4 秒の連続振動
- 止める: 無振動
- 吐く: だんだん弱くなる 8 秒の連続振動

| API 適合 | 実装コスト | LT 映え |
|---|---|---|
| ★☆☆（**duration もエンベロープも表現できない**） | 数時間 | ★★☆ |

**推し所: モールスと同じ「境界」を、まったく違う角度から示せる。**
モールスは「短い持続の対比」が要る。呼吸は「長い持続と強度の変化」が要る。
**どちらも `playHaptics` では書けない。** 2 例あると「たまたま」ではなく**構造的な限界**だと伝わる。

実装は `navigator.vibrate` の PWM でエンベロープを作れる（intensity を時間で変える）ので、
**「web-haptics の PWM がここでは正しく効く」**という § 5.1 の裏返しの例にもなる。

## 3. 会場同期バイブ（Sync Buzz）

登壇者が打つと、会場全員のスマホが同時に震える。

- QR で参加 → WebSocket で「開始時刻」だけ配る → 各端末がローカルで再生
- 応用: ライブ投票の締切を触覚で予告、拍手のタイミング合わせ

| API 適合 | 実装コスト | LT 映え |
|---|---|---|
| ★★☆ | 1日以上（サーバが要る） | **★★★** |

**推し所: 圧倒的につかみが強い。** 冒頭 30 秒で会場の全員のポケットを震わせられれば、
その後 9 分間の注意は確保できる。ただし**会場 Wi-Fi に生死を握られる**のでフォールバック必須。

---

## 4. 触覚ターン・バイ・ターン ナビ

歩行ナビを画面を見ずに。Geolocation + Web Haptics。

- 直進継続: 30 秒ごとに `hint`
- 左折 100m 前: `tick` ×1 / 右折: `tick` ×2
- 曲がる地点: `align`（「ここでピタッと」）
- ルート逸脱: `edge`

| API 適合 | 実装コスト | LT 映え |
|---|---|---|
| **★★★（4 エフェクトの意味論がそのまま UX 語彙になる）** | 半日〜1日 | ★★☆（会場では歩けない） |

**推し所:** アクセシビリティ文脈（視覚障害者の歩行支援）に直結する。
勉強会の質疑が盛り上がりやすい。デモは地図上のシミュレーションで代替できる。

---

## 5. 通知の触覚識別（Haptic Notification Vocabulary）

Slack / メール / カレンダーを**振動パターンだけで**打ち分ける。ポケットの中で誰からか分かる。

- Push API + Service Worker と組み合わせる
- **モールスの応用そのもの**: 送信者のイニシャルをモールスで打つ、という実用アイデアに繋がる

| API 適合 | 実装コスト | LT 映え |
|---|---|---|
| ★★☆ | 半日（Push の設定が面倒） | ★★☆ |

**推し所:** モールスアプリの「実用化したらこうなる」という出口として、
LT の最後に 30 秒で触れると話が綺麗に閉じる。

> ⚠️ Service Worker から `navigator.vibrate` は呼べない（Window コンテキストのみ）。
> 通知の `vibrate` オプション経由になるが、対応がまちまち。**触れるなら事前検証必須。**

## 6. 触覚あてゲーム / 触覚神経衰弱

2 つのカードをタップし、**同じ振動パターンかどうか**で神経衰弱。画面には何も出ない。

| API 適合 | 実装コスト | LT 映え |
|---|---|---|
| ★★☆ | 半日 | ★★★（会場参加型） |

**推し所:** 「人間はどれくらい触覚パターンを識別できるのか」という
**知覚の解像度の話**に持っていける。実は「なぜ API のエフェクトが 4 つしか無いのか」の答えでもある
（＝人間がそれ以上見分けられないから）。**API 設計の合理性を体験で裏付けられる、地味に深い案。**

---

## 7. 触覚パスワード / リズム認証

秘密のリズムを触覚で「教えられ」、それを再現して認証する。

- 覗き見耐性がある（画面に何も出ない）
- セキュリティネタとして単体で LT が 1 本立つ

| API 適合 | 実装コスト | LT 映え |
|---|---|---|
| ★☆☆（duration が要る＝モールスと同じ制約） | 半日 | ★★☆ |

**推し所:** 面白いが、**モールスと制約が丸かぶり**なので今回の LT では冗長。別の機会向け。

---

## 8. 触覚メトロノーム

BPM を振動で。バンド練習でイヤモニの代わり。拍頭だけ `align`、裏拍は `tick`。

| API 適合 | 実装コスト | LT 映え |
|---|---|---|
| ★★★ | **数時間（最小）** | ★☆☆ |

**推し所:** 実装が一番楽。**時間が無いときの保険としてポケットに入れておく価値がある。**
`setInterval` のジッタ問題（AudioContext の時計を使うべき）という別の学びも付いてくる。

---

## まとめ: 今回の LT に組み込むなら

```
【冒頭のつかみ】   #3 会場同期バイブ（余裕があれば）
【正の例】         #1 触覚ノッチ付きスライダー   ← 最優先で作る
【本題・境界の例】 モールス（本体アプリ）
【境界の補強】     #2 呼吸ガイド（30秒だけ触れる）
【出口】           #5 通知の触覚識別（口頭のみ）
```

**#1 だけは必ず作る。** これが無いと「Web Haptics API は使えない」という
不公平な結論に聞こえてしまう。実装コストも数時間なので費用対効果が最も高い。
